# 知识库沉淀 Skill（knowledge-mkdocs）

目标：先按"目标文件"规划并汇报要沉淀的内容，再把用户勾选的文件以与仓库现有文章一致的风格准确写入 `knowledge-mkdocs`，并更新导航。
与学科无关：现场读取仓库结构自适应，技术 / 外语 / 任何主题通用。

## 阶段 1：定位与理解知识库
1. 在工作区找到 `knowledge-mkdocs` 根目录（含 `mkdocs.yml`）。
2. 读 `mkdocs.yml`：掌握 `nav` 结构、分类层级、以及导航标题风格
   （有的板块用 emoji 前缀，如 🌱🌿🌳 表示入门 / 基础 / 进阶）。
3. 浏览 `docs/` 目录树，了解目录划分与文件命名约定。

## 阶段 2：覆盖度核对（对每个候选知识点）
在 `docs/` 目录树、`mkdocs.yml` 的 nav、以及相关文件内容里检索该知识点，分类：
- `[无]`：知识库完全没有 → 新建文件。
- `[不全]`：已有相关文件但缺这部分 → 在既有文件内补写。
- `[已覆盖]`：已有充分讲解 → 不列入待沉淀清单。

## 阶段 3：规划落点（汇报前完成）
把 `[无]` / `[不全]` 的知识点归并到具体的目标文件里：
### 选目录与命名
- 按主题归入**最贴切的既有分类**；找不到合适分类时新建（见"新领域"）。
- **对照同目录相邻文件**决定文件名风格（如 `基础篇00X_标题.md`、序号前缀等），保持一致；
  没有先例时用简洁的 `主题_标题.md`。
- `[不全]` 条目落到既有文件，写明补在哪一节；内容为空的既有文件直接写入。
- 文件名、导航标题和内容要点都按通用知识来命名（见阶段 4"通用化规则"），不带来源项目的名字。
- 一个文件聚焦一个主题，篇幅对齐相邻文章；知识点太多就拆成同系列的多篇。

### 汇报格式
以"目标文件"为单位编号汇报，**不要**按主题列逐条知识点的大表格。每个文件写：
- **目标**：`docs/` 下的完整路径（目录 + 文件名），标明「新建」或「补写 §章节」；
  新建文件同时写出 nav 位置（板块 > 分组 > 导航标题）。
- **要编写的内容**：按文章小节列出要点，每条一句话；所有候选知识点都要落在某个文件里。

汇报开头用一两句话说明已覆盖、不再沉淀的内容；结尾请用户按文件编号勾选，
并说明可以删减要点、改目录或改文件名。

## 阶段 4：撰写（仅限用户勾选的文件）
### 写内容
- 用中文撰写，深度与结构**对齐相邻文章**（标题层级、示例密度、讲解详略）。
- **章节标题从 `##` 开始，正文里不要出现多个 `#` 一级标题**，即使相邻文章这样写也不要照搬：
  Material 主题的右侧目录只显示第一个一级标题下面的内容，用多个 `#` 会导致目录缺失。
- 格式沿用仓库约定：代码用围栏代码块；流程图用 ` ```mermaid `；该板块若用 emoji 前缀则沿用。
- `[不全]` 条目：编辑既有文件补上缺失部分，不新建重复文件。
### 通用化规则（必须遵守）
知识库面向任何读者。知识点可以来自某个真实项目或某次会话，但写出来的内容必须脱离来源也能读懂。
- **不出现来源信息**：项目名 / 仓库名、公司名、人名、用户名、邮箱、本机路径（如 `/Users/xxx`）、
  内部域名、真实的账号密码 / 密钥 / 令牌。
- **示例用中性占位符**：需要项目名、包名时用 `my-service` / `my_service` 这类通用名字，
  同一系列文章保持一致；不写"以 xxx 项目为例""在 xxx 中"。
- **不写过程叙述**：不出现"第 N 步""这次""本次项目""跟做时""当时""回头看""git log 里能看到"
  "实测""已验证"等指向某次工作经历的说法。需要展示真实输出时，写成"运行后会输出：……"。
- **踩坑经验写成通用规律**：按"现象 → 原因 → 解决办法"陈述，不讲是谁、在哪一步遇到的。
- **示例只保留说明知识点所需的部分**：删掉与知识点无关的业务细节。
- 素材里的结论如果只在特定版本或配置下成立，写明前提条件（如工具版本、配置项）。

### 并行撰写（多个文件时）
- 每个文件单独开一个工作流（如单 agent 工作流），并行执行；主会话不逐篇撰写。
- 每个工作流的任务说明必须自包含，写明：本 skill 的路径（要求先读本 skill，并遵守"写内容"和"通用化规则"）、
  目标文件完整路径（新建 / 补写哪一节）、要编写的内容要点、素材来源路径、已核实的事实、
  风格参考文件，以及限制：只改这一个文件、不改 `mkdocs.yml`、不 git commit、不修改素材来源。
- 全部完成后，由主会话统一更新 `mkdocs.yml`（避免并发修改同一文件），再执行阶段 6 的校验。

### 新领域（知识库尚无的主题，如外语）
- 在 `docs/` 下新建顶级目录，并在 `mkdocs.yml` 的 `nav` 顶层新增对应板块。
- 采用**适合该领域**的笔记形式（如语言学习用"词汇 / 语法 / 例句"结构），不硬套技术文档模板。

## 阶段 5：更新导航
- 新建文件：在 `mkdocs.yml` 的 `nav` 对应板块下，按合理顺序插入条目，标题风格对齐同组。
- 补全既有文件：无需改动 nav。

## 阶段 6：校验
- **通用化自查（必做）**：在本次新建 / 修改的文件里搜索素材来源的项目名、包名、用户名、本机路径，
  以及"第 N 步""这次""实测""已验证""跟做"等过程叙述用语（例如
  `grep -n -i -E "<项目名>|<包名>|/Users/|第 ?[0-9]+ ?步|实测|已验证|跟做|这次|本次" <文件>`），
  命中的逐条改成通用写法。补写既有文件时只检查本次新增的部分。
- 若环境装有 mkdocs，运行 `mkdocs build --strict` 验证 nav 与链接；只修正本次改动引入的问题，
  既有文章的历史告警单独告知用户，不擅自处理。
- 未安装 mkdocs 则自查 nav 缩进与文件路径是否一一对应。

## 原则
- 知识库是通用的：内容不依赖某个项目或某次会话也能读懂。
- 只写用户确认过的条目；绝不擅自改动未勾选内容。
- 最小改动：复用既有分类与风格，不做无关重构。
