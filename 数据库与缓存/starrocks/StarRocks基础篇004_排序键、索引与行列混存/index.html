    基础篇003 把数据切开摆放到了各个 Tablet 上。这一篇关注查询怎么在 Tablet 里快速找到需要的数据：排序键与前缀索引、其他索引，以及为高并发点查准备的行列混存。

    本文内容整理自 StarRocks 官方文档：索引、行列混存。版本敏感的内容（语法、参数、特性起始版本）请以你实际部署版本的官方文档为准。本文验证环境为 StarRocks 4.1.x。

    1. 索引概述

    索引是一种特殊的数据结构，相当于数据的目录，能帮查询快速定位到满足条件的数据。StarRocks 的索引分两大类：系统自动创建的内置索引和用户手动创建的索引。

    flowchart TB
    IDX["StarRocks 索引"] --> BUILTIN["内置索引<br/>（自动创建）"]
    IDX --> MANUAL["手动索引<br/>（按需创建）"]
    BUILTIN --> PRE["前缀索引 Prefix"]
    BUILTIN --> ORD["Ordinal 索引"]
    BUILTIN --> ZONE["ZoneMap 索引"]
    MANUAL --> BM["Bitmap 索引"]
    MANUAL --> BF["Bloom Filter 索引"]

    2. 内置索引（自动创建）

    索引 原理 作用
    前缀索引 数据写入时按排序键排序，每 1024 行为一个逻辑数据块，取块内首行排序键值作为索引项 查询条件命中排序键前缀时，快速定位、减少扫描
    Ordinal 索引 列数据按 Data Page 存储（每页约 64 KB），每生成一个页就记一条索引项（含起始行号） 通过行号定位某列数据页的物理位置
    ZoneMap 索引 记录每个数据块的统计信息：Min、Max、是否有 Null 等 查询时据统计快速判断能否整块跳过，减少扫描

    前缀索引是日常建模最该关注的——它直接解释了"为什么排序键列顺序很重要"：只有查询条件命中排序键前缀，前缀索引才生效。这也是排序键设计（高选择性、常用等值过滤列靠前）的依据。前缀索引的长度限制为 36 字节，排序键各列值的长度加起来超过 36 字节时，前缀索引只保存限制范围内的若干前缀列。

    3. 手动索引（按需创建）

    当查询条件列不是排序键前缀时，可以根据数据和查询特点手动建索引：

    索引 适用列 说明
    Bitmap 索引 高基数列，或多个低基数列的组合 过滤性能理想（可过滤掉千分之九百九十九以上的行）
    Bloom Filter 索引 基数较高的列（如 ID 列） 空间高效，但存在一定误判率

    StarRocks 还提供 N-Gram Bloom Filter（加速 LIKE / ngram 函数）、全文倒排索引（加速全文检索）、向量索引（近似最近邻搜索 ANNS）等更专门的索引。

    4. 行列混存

    StarRocks 作为 OLAP 数据库，默认采用列式存储，利于聚合、多表 JOIN 等复杂分析。但自 v3.2.3 起（Beta 特性），它也支持行列混存：数据同时按行和按列两种方式存储，兼顾列存的分析能力和行存的点查能力。

    对比项 列式存储（默认） 行列混存
    存储方式 只按列存 行、列都存（额外一个隐藏的 __row 列把整行编码存起来）
    擅长 复杂分析、聚合、宽表只查少数列 主键高并发点查、低延迟、部分列更新
    代价 — 额外存储开销、导入耗时增加

    什么时候用：当你的主键表既要跑分析、又有大量"按主键点查整行"的在线请求（高并发、低延迟）时，行列混存能让点查走行存的"短路径"（Short Circuit），显著提速。

    基本用法（必须是主键表）：

    -- 先开启 FE 配置项
ADMIN SET FRONTEND CONFIG ("enable_experimental_rowstore" = "true");

CREATE TABLE users (
    id      bigint NOT NULL,
    country string,
    city    string,
    revenue bigint
)
PRIMARY KEY (id)
DISTRIBUTED BY HASH (id)
PROPERTIES ("store_type" = "column_with_row");

    点查时，若 WHERE 条件包含全部主键列、且用 = 或 IN，查询会走行存短路径。可以用 EXPLAIN 验证——计划里出现 Short Circuit Scan: true 说明走了短路径。

    几个要点：① 这是 Beta 特性，仅主键表支持，存算分离集群暂不支持；② 行列混存会明显增加存储占用（行存压缩率通常不如列存）；③ 它可用于在线服务，但点查性能未必能与成熟的 OLTP 数据库相比。

    5. 小结

    • 内置的前缀 / Ordinal / ZoneMap 索引自动生效，其中前缀索引决定了排序键为什么重要。
    • 查询条件不在排序键前缀上时，按需手动建 Bitmap / Bloom Filter 等索引。
    • 行列混存让主键表兼顾分析与高并发点查，代价是额外存储。
