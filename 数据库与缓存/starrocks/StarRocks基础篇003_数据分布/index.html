    基础篇002 定下了数据的语义，这一篇决定数据在集群里怎么摆放——这直接影响查询要扫多少数据、能并行到什么程度。

    本文内容整理自 StarRocks 官方文档：数据分布。版本敏感的内容（语法、参数、特性起始版本）请以你实际部署版本的官方文档为准。本文验证环境为 StarRocks 4.1.x。

    1. 数据分布概述

    StarRocks 采用分区 + 分桶的两级策略，把数据均匀打散到各个 BE 节点：查询时能够有效裁剪数据扫描量，最大限度利用集群的并发性能，从而提升查询性能。

    flowchart TB
    T["一张表"] --> P1["分区 Partition 1<br/>(如 2024-01-01)"]
    T --> P2["分区 Partition 2<br/>(如 2024-01-02)"]
    T --> Pn["分区 Partition n"]
    P1 --> B1["分桶/Tablet 1"]
    P1 --> B2["分桶/Tablet 2"]
    P1 --> B3["分桶/Tablet 3"]
    B1 -.多副本.-> BE1["BE 节点"]
    B2 -.多副本.-> BE2["BE 节点"]
    B3 -.多副本.-> BE3["BE 节点"]
    • 第一层·分区：按分区列（通常是时间/日期）把表拆成更小的管理单元。查询命中分区条件时，可以分区裁剪，直接跳过无关分区，大幅减少扫描量。分区还能针对性地设置存储策略（分桶数、冷热、副本数等）。
    • 第二层·分桶：同一分区内的数据再切成多个桶（bucket），每个桶的数据称为一个 Tablet。Tablet 以多副本（默认 3）均匀分布在 BE 上，既保证高可用，又是并行扫描的最小单元。

    2. 分区

    2.1. 分区方式

    StarRocks 支持三种分区方式（也可以不分区，即全表一个分区）：

    分区方式 适用场景 推荐度
    表达式分区 原称"自动创建分区"，灵活易用，适合大多数场景。按连续日期范围或枚举值查询管理数据时，导入时自动创建分区，无需预建 ⭐ 推荐，未来将逐步取代其他方式
    Range 分区 数据简单有序，按连续日期/数值范围查询管理。需动态、批量或手动创建 特定场景
    List 分区 按枚举值查询管理，且一个分区需包含分区列的多个取值（如一个分区装一个国家下的多个城市） 特定场景

    选择分区列的原则：选能有效裁剪扫描量的列。业务上一般选时间列做分区——既优化"删过期数据"的性能，又方便冷热分级存储。

    分区粒度权衡（综合数据量、查询特点、管理粒度）：

    • 单月数据量小 → 按月分区，减少元数据数量，降低管理和调度开销。
    • 单月数据量大、查询常精确到天 → 按天分区，分区裁剪更精细，扫描更少。
    • 数据要求按天过期 → 按天分区，方便直接删分区。

    表达式分区示例（按天自动建分区）：

    CREATE TABLE site_access(
    event_day DATETIME NOT NULL,
    site_id   INT DEFAULT '10',
    city_code VARCHAR(100),
    pv        BIGINT DEFAULT '0'
)
DUPLICATE KEY(event_day, site_id, city_code)
PARTITION BY date_trunc('day', event_day)
DISTRIBUTED BY HASH(event_day, site_id);

    此外，动态分区可以让 StarRocks 定期提前创建新分区、删除过期分区，实现分区的生命周期管理（TTL）。它和表达式分区的区别是：动态分区按配置提前预建分区，数据不属于预建分区会报错；表达式分区则根据导入数据按需创建。

    3. 分桶

    3.1. 分桶方式

    分区之后必须分桶。StarRocks 主要有两种分桶方式：

    分桶方式 要不要指定分桶键 特点 适用
    随机分桶 不需要（自 v3.1 默认） 数据随机分布到各桶，简单易用 数据量不大、查询性能要求不高；仅支持明细表
    哈希分桶 需要（必须指定分桶键） 相同分桶键值的行落到同一个桶 海量数据、查询常用某些列做过滤条件

    哈希分桶的两大优点：

    1. 提高查询性能：相同分桶键值的行在同一个桶，查询命中分桶键时能裁掉大量无关桶、减少扫描。
    2. 均匀分布数据：选高基数（唯一值多）的列做分桶键，数据能更均匀地散到各桶。

    怎么选分桶键：

    • 如果某列同时满足"高基数 + 经常作查询条件"，首选它。
    • 没有这种列时看查询：复杂查询选高基数列（保证均衡、充分利用资源）；简单查询选常用条件列（提高效率）。
    • 数据倾斜严重时，用多列组合做分桶键（建议不超过 3 列），把数据打散。

    举个例子——site_access 表用 site_id 做分桶键，因为它基数高、且查询几乎都带站点过滤。假设每个分区 10 个桶，WHERE site_id = 54321 的查询能裁掉 9 个桶，只扫 1/10 数据：

    CREATE TABLE site_access(
    event_day DATE,
    site_id   INT DEFAULT '10',
    city_code VARCHAR(100),
    pv        BIGINT SUM DEFAULT '0'
)
AGGREGATE KEY(event_day, site_id, city_code)
PARTITION BY date_trunc('day', event_day)
DISTRIBUTED BY HASH(site_id);

    但如果 site_id 分布极不均匀（少数热门站点占了绝大多数访问，二八分布），单列分桶会造成严重倾斜、形成局部性能瓶颈。此时可以改用 site_id, city_code 组合分桶，把数据划得更均匀。

    短查询 vs 长查询：site_id 单列分桶利于短查询（扫描量小、单机即可完成，减少节点间数据交换）；site_id, city_code 组合分桶利于长查询（扫描量大，靠多机并行提速）。

    3.2. 分桶数量

    • 自动设置（推荐）：自 v2.5.7 起，StarRocks 会根据机器资源和数据量自动决定分桶数，不设 BUCKETS 即可。
    • 手动设置：如果单分区原始数据预计超过 100 GB，建议手动设置。经验法则是每 10 GB 原始数据一个 Tablet，Tablet 大小一般控制在 1～10 GB。

    分桶数设置原则：桶太少，并行度不够；桶太多，Tablet 过多会增加 FE/BE 的元数据管理和调度开销。自 v3.2 起，建表后还可以通过 ALTER TABLE 调整分桶方式、分桶数量和排序键，以适应变化的业务。

    4. 小结

    • 数据分布分两级：分区负责裁剪扫描量和生命周期管理，分桶负责并行度和数据均衡。
    • 分区优先用表达式分区，通常按时间列划分。
    • 分桶键优先选"高基数 + 常用过滤条件"的列，倾斜严重时用多列组合。

    数据摆放好之后，还要让查询能在每个 Tablet 里快速找到需要的行。这就是下一篇 基础篇004 · 排序键、索引与行列混存 的内容。
